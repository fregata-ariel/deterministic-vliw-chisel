## ADR-0001: 実装言語をScalaに統一する

- **状態**: 採用（Issue #2）
- **背景**: Phase 0のアセンブラ・encoder・verifier・参照モデルの実装言語を、PythonとScalaから選ぶ必要があった。
- **決定**: Phase 0〜2のソフトウェアも、Phase 1のChisel RTLもScalaで実装する。
- **理由**:
  - machine description、命令表現、トレース形式を、ビルド上の依存関係としてRTL生成器と直接共有できる。
  - ビルド・テスト・CIが1系統（JDK + sbt）で済む。
  - 「別言語なら参照モデルが独立する」という利点は小さい（ADR-0002）。
- **影響**: `compiler/`・`sim/`・`hw/` はすべてsbtのサブプロジェクトになる。Python実装は作らない。

## ADR-0002: 相互検査は言語ではなく状態表現と判定方法の違いで設計する

- **状態**: 採用（Issue #2。具体化は #8, #9, #10）
- **背景**: 参照モデル・verifier・RTLが同じ誤りを共有すると、相互比較しても誤りを検出できない。実装言語を変えても、同じ人が同じ解釈で書けば誤りは共有される。
- **決定**: 独立性は次の3点で確保する。
  1. **状態表現を変える**: 参照モデルはサイクルごとのpending操作キューで値を計算する。verifierは値を持たず、資源予約表とレジスタの書込み中区間で判定する。
  2. **判定方法を変える**: 参照モデルは実行して、実行時の違反（同一境界の二重書込みなど）を検出する。verifierは命令列だけから静的に合法性を判定する。
  3. **期待値を手で作る**: ISA.mdの命令例のように、commit時刻・最終状態・cycles・拒否理由を人が書いたテストケースを基準にする。モデルの出力をそのままgoldenとして採用する前に、手作りの期待値と照合する。
- **ビルド上の強制**: `compiler`（verifierを含む）と `sim` は `isa` にのみ依存し、互いに依存しない（`build.sbt`）。両者を突き合わせるテストは、テスト専用のプロジェクト `crosscheck` に置く。
- **影響**: 実行意味論は #5 で文書として先に確定し、各実装はその文書から独立に導く。

## ADR-0003: Lean 4は仕様確定後に小さな対象へ限定して導入を検討する

- **状態**: 採用（導入の判断は保留）
- **背景**: 形式検証は決定論性の主張と相性が良い。一方で、仕様が動いている段階で組み込むと重い。また、証明を書かない場合のLean 4は普通の関数型言語であり、書き手が少ないため開発支援（AIエージェントを含む）の精度も下がる。
- **決定**: Phase 0〜1では導入しない。ISAと実行意味論が安定した後、小さな検証対象に限定して導入を検討する。
- **候補**: encoder/decoderの全単射性。MVPの合法性規則の下で、実行サイクル数が入力値に依存しないこと。verifierの規則が意味論上の違反をすべて含むこと。

## ADR-0004: ツールチェーンとバージョン固定

- **状態**: 採用（Issue #2）
- **方針**:
  - バージョンはすべて固定する。採用するのはリリースから2週間以上経った版だけにする。
  - 更新はPRで行い、この表と `build.sbt`・`project/` を同時に変える。
  - Scalaのバージョンは、Phase 1で使うChiselが要求する版に合わせる。

| 対象 | バージョン | 固定場所 | 備考 |
|---|---|---|---|
| JDK | 21 | `.github/workflows/ci.yml` | CIはTemurin |
| Scala | 2.13.18 | `build.sbt` | Chisel 7.16.0 のPOMが要求する版 |
| sbt | 1.12.15 | `project/build.properties` | sbt 2.x はプラグインとChiselの追随を待つ |
| ScalaTest | 3.2.20 | `build.sbt` | ChiselSimと同じテスト基盤 |
| ujson | 4.4.3 | `build.sbt` | JSONの読み書き（ADR-0007） |

- **コンパイラ設定**: `-deprecation -feature -unchecked -Xlint -Werror`。警告はすべてエラーとして扱う。
- **sbtプロジェクト構成**:

## ADR-0005: CIの入口と起動条件

- **状態**: 採用（Issue #3）
- **決定**:
  - 手元とCIの入口を `scripts/check.sh` に一本化する。CIのジョブはこのスクリプトを呼ぶだけにする。
    - `static`: JSON構文、shellcheck、追跡ファイルの空白エラー
    - `scala`: `sbt scalafmtSbtCheck scalafmtCheckAll test`
  - 起動条件は、`main` へのpush、すべてのPR、手動実行とする。作業ブランチではPRを開いてCIを回す。（当初は全ブランチへのpushで起動し、PRでは二重実行を避けてジョブを`if`で飛ばしていたが、PR上に同名のskippedチェックが並び紛らわしいため変更した。）
  - `permissions: contents: read` にする。`main` 以外では、同じrefの古い実行をキャンセルする。
  - 使用するActionは、公式（`actions/*`）とsbt公式（`sbt/setup-sbt`）のメジャータグで固定する。第三者のActionを追加する場合はcommit SHAで固定する。
- mutation チェック（`scripts/mutation-check.sh`）は遅いため、別のワークフロー `mutation.yml` で、手動実行とmutantの定義を変えたPRでだけ実行する（#33）。
- **今後**: Phase 1でChisel・firtool・Verilatorのジョブを追加する。golden traceの比較は #8 以降で `scala` ジョブのテストとして追加する。

## ADR-0006: MVPでは合法なプログラムを保守的に限定する

- **状態**: 採用（Issue #5）
- **背景**: ハザード検査の実装方法を決める前に、命令がいつ値を読み、いつ状態を更新するかという実行意味論を確定する必要があった。現行ISAの骨格（発行サイクルで読む、固定レイテンシー後にcommitする、同一bundle内の直接転送なし）は既に明確だった。
- **決定**: 骨格はそのまま保ち、[ISA.mdの「実行意味論」](ISA.md#実行意味論)として文書化する。合法なプログラムは[「MVPの合法性規則」](ISA.md#mvpの合法性規則) L1〜L8 に限定する。意味論上は値が定義できても、次の使い方は不正とする。
  - 書込み中のレジスタを読み、旧値を利用すること（L3）
  - 同じレジスタへの書込みを重ねること（L4）
  - 入力宣言されていない値を読むこと（L8）
  - HALTを最後以外のbundleに置くこと（L2）
- **理由**:
  - 合法なプログラムでは、各レジスタの値が「最後にcommitされた書込み」だけで決まる。実行中の操作の順序や、ハードウェアのパイプライン内部状態に依存しない。そのため、verifier・参照モデル・RTLが独立に実装しても一致を確認しやすい。
  - MVPのカーネル（展開済みの固定長ループ）では、これらの使い方は不要である。
  - 規則は後から緩められるが、一度許したものを禁止するとプログラムの互換性が失われる。
- **影響**:
  - verifier（#9）は、書込み区間・書戻しポートの予約・入力宣言を使って、L1〜L8を静的に判定する。
  - 参照モデル（#8）は、同じ違反を実行中に検出する。
  - テストケース（#7）は、入力宣言 R_in / M_in を持つ。
  - `config/machine.json` に `instruction_memory.bundles`（256）と `timing.source_read` を追加した。

## ADR-0007: machine.jsonは手書きの厳格なローダで検証し、JCS互換の正規化形式で識別する

- **状態**: 採用（Issue #4）
- **背景**: RTL・命令列・シミュレータが同じ定義を参照するためには、定義の検証方法と同一性の判定方法が必要だった。
- **決定**:
  - 検証は、JSON Schemaではなく、Scalaの手書きローダ（`vliw.isa.MachineDescription`）で行う。規則は [MACHINE.md](MACHINE.md) にまとめる。
  - JSONの読み書きには ujson を使い、重複キーを拒否する厳格な読み込みを被せる。
  - 同一性は、正規化形式（RFC 8785を整数に制限したもの）のSHA-256で表す。`schema_version`（形式の版）と `revision`（内容の版）は分けて持つ。
- **理由**:
  - mvp-0 には、値が1つに固定された項目が多い。「この実装が対応する値か」を判定するには、型の検査だけでなく値の検査が必要で、ローダと同じ場所に書く方が一貫する。
  - JSON Schemaの検証器を追加すると依存が増える。またScalaのモデルとschemaの二重管理になる。
  - 正規化形式は、ASCIIと整数だけの文書では `jq -cS .` と一致する。そのため、外部ツールでも同じhashを再計算できる。
- **影響**: ローダの規則を変えるときは `schema_version` を上げる。CIの `static` ジョブは引き続きJSON構文だけを確認し、意味の検証は `scala` ジョブのテスト（`MachineDescriptionSpec`）が行う。

## ADR-0008: アセンブリ構文とテストケース形式は isa に置く

- **状態**: 採用（Issue #7）
- **背景**: テストケースは、verifier（`compiler`）と参照モデル（`sim`）の両方が読む。`sim` は `compiler` に依存できない（ADR-0002）ため、どちらかに置くと片方から読めない。
- **決定**: アセンブラ、逆アセンブラ、テストケースのローダ、規則IDの一覧（`Rule`）を `isa` に置く。これらは命令の**表記**と**入力・期待値の形式**だけを扱い、実行意味論や合法性の判定を含まない。
- **形式**: テストケースはJSONとし、命令列は文字列の配列として埋め込む（[TESTCASE.md](TESTCASE.md)）。machine description と同じ厳格なローダを使える。命令列も1行1要素で読める。
- **影響**: `compiler` は Phase 2 のスケジューラと verifier を担う。アセンブラは `compiler` に置かない。
