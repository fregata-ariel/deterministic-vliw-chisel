## ADR-0001: 実装言語をScalaに統一する

- **状態**: 採用（Issue #2）
- **背景**: Phase 0のアセンブラ・encoder・verifier・参照モデルの実装言語を、PythonとScalaから選ぶ必要があった。
- **決定**: Phase 0〜2のソフトウェアも、Phase 1のChisel RTLもScalaで実装する。
- **理由**:
  - machine description、命令表現、トレース形式を、ビルド上の依存関係としてRTL生成器と直接共有できる。
  - ビルド・テスト・CIが1系統（JDK + sbt）で済む。
  - 「別言語なら参照モデルが独立する」という利点は小さい（ADR-0002）。
- **影響**: `compiler/`・`sim/`・`hw/` はすべてsbtのサブプロジェクトになる。Python実装は作らない。

## ADR-0002: 相互検査は言語ではなく状態表現と判定方法の違いで設計する

- **状態**: 採用（Issue #2。具体化は #8, #9, #10）
- **背景**: 参照モデル・verifier・RTLが同じ誤りを共有すると、相互比較しても誤りを検出できない。実装言語を変えても、同じ人が同じ解釈で書けば誤りは共有される。
- **決定**: 独立性は次の3点で確保する。
  1. **状態表現を変える**: 参照モデルはサイクルごとのpending操作キューで値を計算する。verifierは値を持たず、資源予約表とレジスタの書込み中区間で判定する。
  2. **判定方法を変える**: 参照モデルは実行して、実行時の違反（同一境界の二重書込みなど）を検出する。verifierは命令列だけから静的に合法性を判定する。
  3. **期待値を手で作る**: ISA.mdの命令例のように、commit時刻・最終状態・cycles・拒否理由を人が書いたテストケースを基準にする。モデルの出力をそのままgoldenとして採用する前に、手作りの期待値と照合する。
- **ビルド上の強制**: `compiler`（verifierを含む）と `sim` は `isa` にのみ依存し、互いに依存しない（`build.sbt`）。両者を突き合わせるテストは、テスト専用のプロジェクト `crosscheck` に置く。
- **影響**: 実行意味論は #5 で文書として先に確定し、各実装はその文書から独立に導く。

## ADR-0003: Lean 4は仕様確定後に小さな対象へ限定して導入を検討する

- **状態**: 採用（導入の判断は保留）
- **背景**: 形式検証は決定論性の主張と相性が良い。一方で、仕様が動いている段階で組み込むと重い。また、証明を書かない場合のLean 4は普通の関数型言語であり、書き手が少ないため開発支援（AIエージェントを含む）の精度も下がる。
- **決定**: Phase 0〜1では導入しない。ISAと実行意味論が安定した後、小さな検証対象に限定して導入を検討する。
- **候補**: encoder/decoderの全単射性。MVPの合法性規則の下で、実行サイクル数が入力値に依存しないこと。verifierの規則が意味論上の違反をすべて含むこと。

## ADR-0005: CIの入口と起動条件

- **状態**: 採用（Issue #3）
- **決定**:
  - 手元とCIの入口を `scripts/check.sh` に一本化する。CIのジョブはこのスクリプトを呼ぶだけにする。
    - `static`: JSON構文、shellcheck、Python の構文、追跡ファイルの空白エラー、ChiselSim のテストが `VliwChiselSim` を使うこと、mutation の判定と再実行の自己テスト（#74）、`scripts/toolchain.sh` の自己テスト（#121）、workflow が Verilator と JDK を `.github/actions/setup-toolchain` でだけ入れることとその自己テスト（#121）
    - `scala`: `sbt scalafmtSbtCheck scalafmtCheckAll test`
  - 起動条件は、`main` へのpush、すべてのPR、手動実行とする。作業ブランチではPRを開いてCIを回す。（当初は全ブランチへのpushで起動し、PRでは二重実行を避けてジョブを`if`で飛ばしていたが、PR上に同名のskippedチェックが並び紛らわしいため変更した。）
  - `permissions: contents: read` にする。`main` 以外では、同じrefの古い実行をキャンセルする。
  - 使用するActionは、公式（`actions/*`）とsbt公式（`sbt/setup-sbt`）のメジャータグで固定する。第三者のActionを追加する場合はcommit SHAで固定する。
- mutation チェック（`scripts/mutation-check.sh`）は遅いため、別のワークフロー `mutation.yml` で、手動実行とmutantの定義を変えたPRでだけ実行する（#33）。mutation のスクリプト（`mutation-check.sh`・`mutation-classify.py`）とワークフロー自体を変えたPRでも実行する（#74）。ツールチェーン（`project/toolchain.properties`、`.github/actions/setup-toolchain`、`scripts/toolchain.sh`・`scripts/verilator-build.sh`、`Toolchain.scala`・`VliwChiselSim.scala`）を変えたPRでも実行する（#121）。
- `scala` ジョブ（と `mutation` ジョブ）は Verilator を apt で入れ（ADR-0020 で置き換えた。Verilator と JDK は、CI の action [.github/actions/setup-toolchain](../.github/actions/setup-toolchain/action.yml) が `project/toolchain.properties` の版で入れる。入れ方は [docs/toolchain/README.md](toolchain/README.md) にある）、`hw` の ChiselSim テストも実行する（#23）。firtool は sbt の依存として取得し、sbt のキャッシュに載る。
- 間欠的な失敗を追えるよう、`scripts/check.sh` は sbt の出力・環境・プロセスの記録・テストの並行性の実効設定を `build/check-logs/` に残し、`scala` ジョブは失敗したときにそれらと ChiselSim の作業ディレクトリ・JUnit レポートを artifact として残す。テストが止まったときは、`check.sh` が `CHECK_TIMEOUT` で sbt を止めて失敗を記録し、ステップの timeout（job より短い）は予備とする。ステップの timeout が止めるのは外側のシェルだけで、sbt は動き続け、失敗の記録も残らないからである。`mutation` ジョブは mutant ごとの判定とログを常に残す。繰り返し実行のワークフロー `repeat-tests.yml` は手動実行だけとする（#74）。

## ADR-0006: MVPでは合法なプログラムを保守的に限定する

- **状態**: 採用（Issue #5）
- **背景**: ハザード検査の実装方法を決める前に、命令がいつ値を読み、いつ状態を更新するかという実行意味論を確定する必要があった。現行ISAの骨格（発行サイクルで読む、固定レイテンシー後にcommitする、同一bundle内の直接転送なし）は既に明確だった。
- **決定**: 骨格はそのまま保ち、[ISA.mdの「実行意味論」](ISA.md#実行意味論)として文書化する。合法なプログラムは[「MVPの合法性規則」](ISA.md#mvpの合法性規則) L1〜L8 に限定する。意味論上は値が定義できても、次の使い方は不正とする。
  - 書込み中のレジスタを読み、旧値を利用すること（L3）
  - 同じレジスタへの書込みを重ねること（L4）
  - 入力宣言されていない値を読むこと（L8）
  - HALTを最後以外のbundleに置くこと（L2）
- **理由**:
  - 合法なプログラムでは、各レジスタの値が「最後にcommitされた書込み」だけで決まる。実行中の操作の順序や、ハードウェアのパイプライン内部状態に依存しない。そのため、verifier・参照モデル・RTLが独立に実装しても一致を確認しやすい。
  - MVPのカーネル（展開済みの固定長ループ）では、これらの使い方は不要である。
  - 規則は後から緩められるが、一度許したものを禁止するとプログラムの互換性が失われる。
- **影響**:
  - verifier（#9）は、書込み区間・書戻しポートの予約・入力宣言を使って、L1〜L8を静的に判定する。
  - 参照モデル（#8）は、同じ違反を実行中に検出する。
  - テストケース（#7）は、入力宣言 R_in / M_in を持つ。
  - `config/machine.json` に `instruction_memory.bundles`（256）と `timing.source_read` を追加した。

## ADR-0007: machine.jsonは手書きの厳格なローダで検証し、JCS互換の正規化形式で識別する

- **状態**: 採用（Issue #4）
- **背景**: RTL・命令列・シミュレータが同じ定義を参照するためには、定義の検証方法と同一性の判定方法が必要だった。
- **決定**:
  - 検証は、JSON Schemaではなく、Scalaの手書きローダ（`vliw.isa.MachineDescription`）で行う。規則は [MACHINE.md](MACHINE.md) にまとめる。
  - JSONの読み書きには ujson を使い、重複キーを拒否する厳格な読み込みを被せる。
  - 同一性は、正規化形式（RFC 8785を整数に制限したもの）のSHA-256で表す。`schema_version`（形式の版）と `revision`（内容の版）は分けて持つ。
- **理由**:
  - mvp-0 には、値が1つに固定された項目が多い。「この実装が対応する値か」を判定するには、型の検査だけでなく値の検査が必要で、ローダと同じ場所に書く方が一貫する。
  - JSON Schemaの検証器を追加すると依存が増える。またScalaのモデルとschemaの二重管理になる。
  - 正規化形式は、ASCIIと整数だけの文書では `jq -cS .` と一致する。そのため、外部ツールでも同じhashを再計算できる。
- **影響**: ローダの規則を変えるときは `schema_version` を上げる。CIの `static` ジョブは引き続きJSON構文だけを確認し、意味の検証は `scala` ジョブのテスト（`MachineDescriptionSpec`）が行う。

## ADR-0008: アセンブリ構文とテストケース形式は isa に置く

- **状態**: 採用（Issue #7）
- **背景**: テストケースは、verifier（`compiler`）と参照モデル（`sim`）の両方が読む。`sim` は `compiler` に依存できない（ADR-0002）ため、どちらかに置くと片方から読めない。
- **決定**: アセンブラ、逆アセンブラ、テストケースのローダ、規則IDの一覧（`Rule`）を `isa` に置く。これらは命令の**表記**と**入力・期待値の形式**だけを扱い、実行意味論や合法性の判定を含まない。
- **形式**: テストケースはJSONとし、命令列は文字列の配列として埋め込む（[TESTCASE.md](TESTCASE.md)）。machine description と同じ厳格なローダを使える。命令列も1行1要素で読める。
- **影響**: `compiler` は Phase 2 のスケジューラと verifier を担う。アセンブラは `compiler` に置かない。

## ADR-0009: machine description の契約を3段に分け、II と書込み中のメモリ語を合法性規則にする

- **状態**: 採用（Issue #35。第三者レビュー P1）
- **背景**: ローダは `ii` と `latency` を1〜8で受け付けるが、verifier と参照モデルは II を検査せず、RTL は一部の構成だけを実装していた。どの構成をどこまで扱えるかが文書になく、構成を変えた実験で契約が割れるおそれがあった。また ST のレイテンシーが2以上のとき、書込み中の番地を LD で読む（旧値を読む）ことの扱いが未定だった。
- **決定**:
  - 契約を、形式（ローダ）・意味論（verifier と参照モデル）・RTL（`CoreParams`）の3段に分ける。ローダが受け付ける構成は、すべて意味論で扱う。RTL の対応範囲は別に定め、範囲外は組み立て時に拒否する（[MACHINE.md](MACHINE.md)「実装ごとの対応範囲」）。
  - II は、演算ごとの専用の演算器の発行間隔とする。同じ演算の発行は II 以上空ける（L9）。演算器の共有は mvp-0 では表現しない。
  - 書込み中のメモリ語の読出しを禁止する（L10）。レジスタの L3 と同じ扱いで、旧値が定義されていても不正とする。
- **理由**:
  - II を検査しなければ、II が2以上の構成で、verifier・参照モデルが II を守らない命令列を合法と判定してしまう。拒否するより規則にする方が、Phase 2 のスケジューラで資源予約を試せる。検査の実装も小さい。
  - L10 は、ADR-0006 の方針（実行中の操作の時刻に依存するプログラムを排除する）に従う。旧値の読出しを許すと、ST のレイテンシーを伸ばす RTL は旧値を保持する仕組みを持つ必要がある。規則は後から緩められる。
  - 汎用ローダで RTL の非対応値を一律に拒否すると、ソフトウェアだけで行う実験（`slow_units.json` など）ができなくなる。
- **影響**:
  - 凍結した `config/machine.json`（revision 2）は、全 II が1、ST のレイテンシーが1なので、L9・L10 は常に満たされる。既存の判定・hash・ISA バージョン（`mvp-0`）は変わらない。
  - 構成を変えたテストケースは判定が変わることがある（`slow_store_then_load` は L8 に加えて L10 に違反する）。
  - verifier と参照モデルの差分テストに、II が2以上の構成（`tests/machines/ii_units.json`）を加えた。

## ADR-0010: カーネルDSLは Scala 内部DSLとし、配置と lowering を分ける

- **状態**: 採用（Issue #47）
- **背景**: Phase 2 では、SAXPY・FIR・行列積を自動で命令列にし、構成を変えて比べる。そのための入力の書き方と、意味（期待値）を決める必要があった。
- **決定**:
  - Scala の内部DSLとする（[DSL.md](DSL.md)）。ループは Scala の `for` で展開する。値は32bitの整数で、2^32 を法とする。
  - 式は、物理レジスタ・発行サイクル・アドレスを持たない仮想値（`Expr`）として表す。DAG、スケジューリング、レジスタ割り当ては後の段階で行う。
  - Scratchpad のアドレスは DSL に書かず、別の処理（`MemoryLayout`）で決める。初期実装は固定順の割り当てとする。
  - スカラーと定数は、初期化済みメモリの読出しに lowering する（現在の ISA に即値演算が無いため）。
  - 意味は、DSL を直接評価する参照実装（`Interpreter`）で定める。テストでは、DSL を使わない素の Scala の実装とも比べる。
  - 入力は読出し専用、出力は書込み専用で、各出力要素にちょうど1回だけ代入する。
- **理由**:
  - 目的は将来のアーキテクチャ比較で、DSL の機能ではない。内部DSLならパーサが要らず、Scala の型検査と `for` をそのまま使える（[ADR-0001](#adr-0001-実装言語をscalaに統一する)）。
  - 配置と DSL を分けると、配置の方法（bank を考えた割り当てなど）を変えて比べられる。
  - 読出し専用の入力と書込み専用の出力なら、3つのカーネルを書けて、メモリ操作の alias が起きない。DAG（#48）の最初の実装が単純になる。
- **影響**: SAXPY は `y = a*x + y` を上書きせず、別の出力配列に書く。上書きや中間配列が必要になったら、制約を緩め、DAG にメモリ順序の依存を加える。

## ADR-0011: Phase 3 のループは ISA を変えずに展開し、IR に反復の情報を残す

- **状態**: 採用（Issue #67、オーナー判断 2026-10-15。第三者レビューの推奨）
- **背景**: Modulo Scheduling は反復を重ねる手法で、反復の単位と反復をまたぐ依存（RecMII）が要る。mvp-0 には分岐もループも無く、Phase 2 の DSL は組み立て時に完全に展開するので、DAG には反復の情報が残らない。
- **決定**:
  - mvp-0 の ISA は変えない。Modulo Scheduling の結果は、有限の反復回数からプロローグ・定常・エピローグを直線の bundle 列に展開して出力する（案A）
  - DSL または IR に、反復の境界、反復距離付きの依存、最小限のループ内の状態を残す（#76）
  - 演算器の II（`operations.<op>.ii`、L9）と、ループの II（反復の開始間隔。`vliw-metrics/1` の `ii` 欄）を別の概念として扱う
  - 展開した結果が命令領域（`instruction_memory.bundles`）を超える場合は、展開できないと報告する
  - ISA の固定回数ループ命令（案B）は先送りする（#81）
- **理由**: ISA・verifier・参照モデル・RTL を変えずに、Modulo Scheduling そのものの効果と限界を先に測れる。ループ命令を同時に入れると、命令領域の大きさやループ制御のオーバーヘッドの影響と切り分けられない。
- **影響**: ADR-0010 の「ループは Scala の `for` で展開する」を部分的に置き換える（ループ構造を IR に渡す経路を #76 で足す。完全に展開する既存の書き方は残してよい）。最終の命令列は既存の verifier（L1〜L10）・参照モデル・RTL でそのまま検査できる。反復回数は命令領域の容量で制限される。案Bは、M3 の結果（命令領域に収まらないカーネル、命令数と cycles）と、案Bのループ制御の cycles の見積りを材料に判断する（#81）。

## ADR-0012: MAC を先に導入して評価し、SIMD は後に分ける

- **状態**: 採用（Issue #69、オーナー判断 2026-10-15。第三者レビューの推奨）
- **背景**: Phase 2 の `fir4x8` と `matmul3` は Compute スロットが律速で、MUL と ADD の組が多い。MAC・SIMD・Compute スロットの増設を同時に入れると、どの変更が cycles・面積・Fmax に効いたかを切り分けられない。
- **決定**:
  - Milestone 3 では MAC だけを扱う。契約（演算の形、RF の読出しポート、ハザード、Latency・II、エンコード、ISA の版）は #69 で決め、実装と、MAC のある構成とない構成の cycle ベースの比較は #77 で行う
  - Fmax・面積・RF の増分のコスト（Phase B）は、#77 の構成を使って合成評価 #57 で行う。M3 で選ぶ読出しポートの方式は暫定とし、その結果で見直す
  - SIMD と Compute スロットの増設は、MAC 単独の効果を測った後に、別の実験として設計する（#78）
  - 凍結した mvp-0（revision 2）は変えない。MAC は新しい ISA の版で入れる
- **理由**: 変更を1つずつ入れると、効果の原因を切り分けられる。MAC は cycles を減らしても、RF のポートや演算器の面積を増やし得るので、cycle と面積・Fmax を分けて評価する必要がある。
- **影響**: ROADMAP の Phase 3 は「Modulo Scheduling、MAC」とし、SIMD は MAC の評価の後に置く。

## ADR-0013: ChiselSim の Verilator は1スレッドで verilate し、乱数の seed を明示する

- **状態**: 採用（Issue #74）
- **背景**: 手元で、テストがまれに失敗した（Verilator のビルドの `make: *** [Makefile:12: simulation] Error 255` など）。CI ではまだ起きていなかった。失敗したビルドのログを残すようにしたところ、mutant を入れない `sbt test` で再現した。C++ のビルドが終わった後、`verilator_bin` が終了するときに `%Error: Internal Error: attempted to destroy locked Thread Pool` で abort していた。
  - 原因は Verilator 5.020 の不具合（upstream issue 4931）である。スレッドプールの破棄の処理が、プールのロックを1回だけ試す。終了の直前に起こされた worker がロックを持っていると abort する。
  - svsim の既定は `-j 0` で、verilation もコアの数のスレッドで行う。このため、ビルドのたびにこの abort が起こりうる。
  - 測定（同じ設計の verilation だけを繰り返した）では、複数スレッドで 8/9663 回（約 0.08%）abort した。`--verilate-jobs 1` では 0/6000 回だった。1回の `sbt test` は少なくとも 53 回ビルドするので、1回の `sbt test` が失敗する確率は約 4% になる。
  - 修正は Verilator 5.024・5.026 で入り、5.030 でこの処理は書き直された。ubuntu-24.04 の apt には 5.020 しかない。
- **決定**:
  - ChiselSim のテストは `vliw.hw.VliwChiselSim` を mix in する（`scripts/check.sh static` が `with ChiselSim` を拒否する）
  - `VliwChiselSim` は Verilator に `--build-jobs 0 --verilate-jobs 1` を渡す。verilation は1スレッドで行い、C++ のビルドは今までどおり全コアで行う
  - `VliwChiselSim` は乱数の seed を `+verilator+seed+<n>` で明示し、記録する（`VLIW_SIM_SEED`、既定 1）。Verilator 5.020 は seed がないと毎回同じ状態から乱数を始めるが、その値は版に依存し、どこにも記録されないからである
- **理由**:
  - verilation が1スレッドなら worker スレッドがなく、プールのロックも無効になる。このため、この abort は起こらない（5.020 のソースと、スレッド数の測定で確認した）
  - verilation は1回 0.1〜0.2 秒で、ビルドの大半は C++ のコンパイルである。このため、1スレッドにしても時間はほとんど変わらない
  - Verilator の版は ADR-0004 で固定しており、CI の環境では上げられない（ADR-0020 で置き換えた。版は `project/toolchain.properties` の1行で変え、候補は PR から試す）
- **影響**: Verilator を 5.030 以降に上げるときは、この設定を外せるかを確かめる。`scripts/verilator-exit-race.py` で、同じ設計の verilation を繰り返し、構成ごとに abort の回数を数えられる。調べた経過と数値は #74 に記録する（ADR-0020 で、記録先を #121 と `docs/toolchain/` に移した）。

## ADR-0014: ループ IR では状態をレジスタで渡し、ループ不変の値と後の反復が再び読む語をレジスタに保持する

- **状態**: 採用（Issue #76）
- **背景**: Modulo Scheduling（#68）には、反復の単位と、反復をまたぐ依存が要る（ADR-0011）。Phase 2 の DSL は組み立て時に完全に展開する。ループ構造を保つ IR を作るにあたり、ループ内の状態（累算など）の渡し方と、複数の反復が同じ語を読む値の扱いを決める必要があった。
- **決定**:
  - ループ構造を保ったまま IR を組み立てる API（`vliw.compiler.loop.LoopKernel`）を足す。Phase 2 の DSL（`dsl.Kernel`）とその `for` の展開は変えない
  - ループ内の状態はレジスタで渡す。状態は、初期値（ループの前に計算する）と次の反復の値（各反復の演算）で表す。入力は読出し専用、出力は書込み専用のままとする（ADR-0010 を変えない）
  - ループ不変の値（stride 0 の語。`saxpy8` の `a`、FIR の係数 `h`、行のループにした `matmul3` の `b`）は、ループの前に1回だけ LD し、全反復でレジスタに保持する
  - 隣の反復と同じ語を読む値（FIR の `x(i+t)`）は、その語を最初に読む反復の LD の値を、反復距離付きのレジスタ依存として後の反復に渡す。ループのどの反復も最初に読まない語（最初の反復より前の反復が読むはずの語）は、ループの前に LD する
  - 状態の次の値は演算（`+`・`-`・`*`）に限る。行列積の m についての累算では、m = 0 の項を状態の初期値にする
- **理由**:
  - 状態をメモリで渡すと、反復をまたぐ依存が LD・演算・ST を通る。既定の構成の `p ← p × x(i)` では LD 2 + MUL 2 + ST→LD 1 = 5 cycles になる。レジスタなら MUL の 2 cycles で、#68 が期待する RecMII（既定の構成で 2、`slow_units` で 3）になる。メモリで渡すには ADR-0010 の制約を緩め、メモリ順序の依存と alias を扱う必要がある。#70 の rematerialization でも、書込みのある語を除く必要が生じる。MAC（#69 の `rd = low32(rs1*rs2+rs3)`）は、レジスタの状態の `acc ← acc + a*b` にそのまま使える
  - レジスタに保持すると、記録するループの LD の数が list scheduling の DAG と同じになる（`saxpy8` 17、`fir4x8` 15、`matmul3` 18）。このため、#68 の比較に LD の数の違いが混ざらず、Memory の ResMII も上がらない。毎反復 LD すると、`saxpy8` の1反復あたりの Memory の操作は3でなく4になり、`fir4x8` の LD は、`x` を毎反復読むと 36、係数も毎反復読むと 64 になる
  - 次の値を演算に限ると、状態は必ず各反復に自分の演算のノードを持つ。共有した LD をそのまま状態にすると、反復距離が合わなくなる。Phase 3 で使う状態（累算、積）はすべて演算である
  - m = 0 を初期値にすると、定数 0 の語と9つの ADD が増えない。展開した結果が `Benchmarks.matmul(3)` と同じになり、メモリ配置も DAG も Phase 2 と同じになる（#68 は同じ配置で比べる）
- **影響**:
  - LD を共有するのは、ループの前の LD（stride 0 の読出しと初期値）どうしと、同じ stride で読む LD の組の中だけである。同じ語を stride 0 と stride のある LD の両方で読むループや、違う stride で読むループでは、その語を2回以上 LD する。また、ループ本体はどの反復でも同じなので、使われない値（格納しない状態の、最後の反復の次の値）の LD と演算も残る。LD の数が list scheduling の DAG と同じになるのは、各配列を1つの stride で読み、すべての値を使うループである。記録する6つのループはこれに当たる（`LoopGraphSpec` が確かめる）
  - 状態と保持する値は、ループの間レジスタを占める。#68 は、これらをレジスタの生存期間に数える（spill はしない）。毎反復 LD する方式が必要になったら、#70 の rematerialization として足す（#70 は list scheduling にだけ入れた。ADR-0016）
  - `matmul3` の累算のループは2反復で、ループの前に LD 6つと MUL 9つがある。1反復の演算は18で、RecMII（ADD の 1）は ResMII より小さい。RecMII が II を決める例は `product` で確かめる（#68）
  - FIR のタップのループは作らない。係数は値で重複を除いた定数なので、`h(t)` は一般に反復番号の一次式のアドレスにならない。累算のループは `matmul3` の m と `dot` で表す
  - ADR-0011 の「ループ構造を IR に渡す経路」は、この API である。ADR-0010 は置き換えない

## ADR-0015: Modulo Scheduling は II を下限から順に試し、最初に命令列ができた II を使う

- **状態**: 採用（Issue #68）
- **背景**: ADR-0011（案A）で、ループは ISA を変えずに、プロローグ・定常・エピローグを直線の命令列に展開すると決めた。#68 は、MII を求め、候補の II で予約表を調べ、レジスタが足りなければ次の II を試し、反復が重ならない II まで収まらなければ理由付きのエラーにすることを求める。II を MII より上げた原因を、(a) 予約表に置けない、(b) レジスタの不足、に分けて記録する。設計のレビューで、番号の順・後戻りなしの単純な配置は、予約表がある II でも失敗することが分かった（`fir4x8` は II 8 で置けるのに II 10 になった）。
- **決定**:
  - II は MII から、1反復だけを list scheduling した長さ（上限）まで順に試す。最初に、予約表に置けて、レジスタと命令領域に収まった II を使う。cycles 最小の II は探さない
  - 配置は、Each のノードを番号の順に、依存の範囲の中で最初に空いている時刻に置き、後戻りしない。失敗したら、残りのノードがまだ予約表に収まるかの先読みを足して、もう一度置く
  - 予約表に収まるか（依存を無視して）は、正確な探索（`RowFit`）で判定する。(a) は「予約表が存在しない」ことに限り、予約表があるのに配置の順で置けない場合（`NoTime`）とは分けて記録する
  - 上限の II で配置に失敗したら、1反復の list schedule をそのまま使う（反復が重ならないので、modulo schedule になる）
  - 展開した命令列は直線のまま、既存の `RegisterAllocator.allocate` でレジスタを割り当てる。spill と rematerialization はしない
  - ループの前のノードは使う側からできるだけ遅く、ループの後のノードは作る側からできるだけ早く置く
  - 記録する II は、トレースで確かめた値とする。照合は表 (bundle, スロット) → (ノード, 反復) とループのグラフだけを使い、スケジュール・レジスタ・展開した DAG を使わない（ADR-0002）
- **理由**:
  - #68 の手順（候補の II を順に試し、収まらなければ次の II）どおりで、結果が決定的である。先読みは、先読みなしで置けるときは同じ結果になり、置けないときだけ働く。記録したループと構成では、予約表が存在する最小の II で配置できる
  - 正確な判定があると、(a) を「この II では原理的に置けない」と言い切れる。配置の順の問題を (a) に数えると、ループの性質と配置の手順の限界が混ざる
  - 上限を1反復の長さに固定すると、探索は必ず終わる。最後に残る失敗の理由は、レジスタか命令領域だけになる
  - 展開した命令列は各反復の値が別の仮想レジスタなので、modulo variable expansion が要らない。list scheduling と同じ割り当てと verifier をそのまま使える
- **影響**:
  - cycles は II について単調でない（`matmul3` の行のループは II 20 で 87 cycles、II 21 で 70 cycles）。記録の Modulo Scheduling の側は1つの戦略であり、cycles 最小とは限らないことを記録に書く
  - 反復回数が少ないループでは、プロローグとエピローグの分が大きく、list scheduling より cycles が多くなりうる。記録した4つのループはどれも、list scheduling の cycles 最小（方式ごとに cycles 最小の系列の vliw）より cycles が多い（[benchmarks/MODULO.md](../benchmarks/MODULO.md)）
  - レジスタが足りないと II が上がり、どの II にも収まらないループは不成立になる（`slow_units` の `matmul3` の累算）。spill や rematerialization（#70）を組み合わせるときは、この ADR を見直す
  - 予約表の正確な判定は、II が62以下で、探索が手数の上限（`RowFit.Budget`）に収まるときだけ行う。それ以外は「決まらない」とする。1反復全体の予約表の判定が決まらない II は (a) とは記録せず、配置は（先読みも）試す。先読みの判定が決まらないときは、その時刻を受け入れ、以降はその II の先読みをしない。1反復全体の判定が決まらないまま配置に失敗した II は `NoTime` に「予約表があるかは決まらない」と付けて記録するので、配置の順の問題と原理的に置けないことの区別は、その II では付かない
  - 2026-10-17 の補足（#119、#68 の第三者レビュー）: 配置の手順や II の選び方を変えるときは、同じ `LoopGraph` と machine で、今の手順と新しい手順を比べる。II を MII から探索の上限まで全て試し、II ごとに、収まらない理由（今と同じく (a)、`NoTime`、(b)、命令領域に分ける）か、命令列ができたときの cycles・同時に生きる値・bundle 数を記録する。最初に命令列ができた II の cycles だけで、手順の良し悪しを言わない（`matmul3` の行のループは II 20 で 87 cycles、II 21 で 70 cycles）

## ADR-0016: rematerialization は行き詰まる試行でだけ、書込みのない語の LD をレジスタの詰まりで複製する

- **状態**: 採用（Issue #70）
- **背景**: register allocation（#50）は、同じ語を1回だけ読む（LD を共有する）まま、レジスタの上限付きでスケジュールし直す。spill はしない。このため、12本では `matmul3` が、8本では `fir4x8` と `matmul3` が、どの試行でも収まらず、レジスタ数を変えた比較ができなかった。入力・スカラー・定数は Scratchpad に残っているので、値を捨てて再び LD できる。複製をいつ、どの LD について作るか、試行と戦略を固定した系列（#79）にどう入れるかを決める必要があった。
- **決定**:
  - 複製してよいのは、DAG のどの ST も書かない語の LD だけとする。ST のある語の LD は複製しない。計算した値と、ループの状態（ADR-0014）は複製しない
  - 上限付きの試行が、どの語も1回だけ読むままで行き詰まるときだけ、複製を作る。行き詰まらない試行のスケジュールは変えない
  - 複製を作る試行は、最初からやり直し、レジスタの上限がスロットを空ける最初の cycle（詰まり）で止まる。置いた LD のうち、置いた読む側と置いていない読む側の両方があるものから、次の使用が最も遠いもの（置いていない読む側の最高の優先度が最も低いもの。同じならば番号の小さい方）を選び、置いていない読む側を新しい LD に付け替える。DAG を作り直して、最初からやり直し、前に止まった cycle 以降の最初の詰まりで止まる（それより前の cycle の詰まりは、候補があっても見送る）。候補がなければ、その詰まりは見送り、その後の最初の詰まりで止まる
  - 複製は付け替える読む側の最小の番号に入れ、後の番号を1つずつ増やす（番号は位相順のまま）
  - 試行の組（優先度 × 上限なし・`loadReserve`）は変えない。複製は戦略の新しい次元にしない。コンパイラは cycles 最小、同じならば LD の少ない方、同じならば先の試行を選ぶ
- **理由**:
  - 書込みのない語は、いつ読んでも同じ値なので、複製にメモリ順序の辺が要らず、DAG の値も変わらない。ST のある語は、読み直す時刻によって値が変わり、ST との順序の辺が要る
  - 最後に行き詰まった時点だけで1つずつ複製すると、改善が小さい（既定の構成の8本で `fir4x8` は 91、`matmul3` は 80 cycles）。詰まりごとに1つずつ複製すると 70 と 61 cycles になる。全ての LD を読む側ごとに分ける単純な方式（どの語も読む側の数だけ LD する）は、`fir4x8` の LD が 64、`matmul3` が 54 になり、Memory スロットで 78 と 68 cycles になる（8・12・16 本とも）。`saxpy8` は `a` を8回読んで 26 から 33 cycles になる。複製を、試行のやり直しで作り、新しいノードの優先度を DAG から求め直すので、スケジューラの途中で値を捨てる仕組みが要らない
  - 行き詰まる試行に限ると、今収まる試行の結果は変わらず、16本の既定の構成の記録（方式ごとに cycles 最小の系列）も変わらない。常に複製を許すと、16本でも結果が変わる（`matmul3` は 54 cycles になるが、vliw の critical-path、reserve 1 の行は 56 から 63 cycles に、単一発行の `matmul3` は 75 から 77 cycles に悪くなる）
  - 試行の組を変えないので、レジスタ数を変える比較（[benchmarks/README.md](../benchmarks/README.md)「比較の書き方」）の取り決め（優先度と `loadReserve` が同じ行どうし）をそのまま使える。複製を次元にすると、上限付きの行が2倍になり、取り決めも変える必要がある
- **影響**:
  - 8・12・16 本で3カーネルとも収まる（既定の構成の vliw で 28 / 70 / 61、26 / 66 / 55、26 / 65 / 56 cycles。[benchmarks/REGISTERS.md](../benchmarks/REGISTERS.md)）。`slow_units` の `matmul3`（16本）は 60 から 57 cycles になる
  - 行き詰まらない試行は複製しないので、方式ごとに cycles 最小の系列でも、レジスタの少ない方が速いことがある（既定の構成の vliw の `matmul3` は、12本で 55 cycles、16本で 56 cycles）。16本で常に複製を許せば 54 cycles になるが、上の理由で採らない。この差は、レジスタ数の効果ではなく、複製を作る条件の効果である
  - 戦略を固定した系列で、16本でも、今まで「上限の下で行き詰まる」だった行の一部が成立し、cycles と LD の数を持つ（既定の構成の vliw で、`fir4x8` の critical-path の reserve 1〜5、`matmul3` の critical-path の reserve 0・4・5 と program-order の reserve 4〜8）。[benchmarks/MODULO.md](../benchmarks/MODULO.md) の比較の表の行も変わる。理由「上限の下で行き詰まる」は、複製を作っても行き詰まることを意味するようになる
  - 同じ行の比較で、レジスタの少ない方が速いことがある。レジスタの多い方の行は複製なしで収まり、少ない方の行は行き詰まって複製を作るからである（既定の構成の `matmul3`、program-order、reserve 3 は、12本で 58 cycles、16本で 63 cycles）。比較の記録には、各行の LD の数を併記する
  - 8本未満では、全ての LD を分ける方式の方が速いことがある（4本の `matmul3` は、この方式で 102 cycles、全てを分けると 85 cycles）。3本では、この方式では `fir4x8` と `matmul3` が収まらない
  - Modulo Scheduling（ADR-0015）は複製をしない。組み合わせるときは ADR-0015 を見直す

## ADR-0017: 資源条件を揃えた固定パイプラインは、スケジュールから生成し、Core の演算器と Scratchpad をそのまま使う

- **状態**: 採用（Issue #75）
- **背景**: 単一発行・VLIW に加え、命令メモリ・命令制御・RF を持たないカーネル専用の回路（固定パイプライン）と比べると、プログラマビリティのコストと専用化の利得を分けて評価できる（[DESIGN.md](DESIGN.md)「評価と拡張」）。#75 は、その第1段階として、資源条件（算術、カーネル、入力と配置、Scratchpad の容量・bank・ポート・1サイクル1アクセス、演算器の種類・レイテンシー・II、Compute の発行と書戻しが1サイクルに1つ、MUL→ADD の連結なし）を揃えた回路の機能と cycles を記録することを求める。回路の作り方を3つ試作して比べた。スケジュールから生成する方式、カーネルごとにループのパイプラインを手で書く方式、Modulo Scheduling の結果からループの制御を生成する方式である。
- **決定**:
  - 回路（`vliw.hw.FixedPipeline`）は、静的なスケジュール（`FixedPlan`。各操作の発行サイクルと、読む値）から生成する。制御はサイクルカウンタとその値の decode で、選択・有効・アドレスはすべてサイクルの定数である。値は32bit のレジスタに置く
  - データパスは Core の `ComputeSlot` と `MemorySlot` をそのまま使う。演算器、書戻しの予約（L5）、bank 分割した 1RW の Scratchpad と1サイクル1アクセスが、構造の上で Core と同じになる
  - 回路と計画の型は `hw` に置き、`hw` は `isa` にだけ依存したままにする。計画は組み立て時に `FixedPlan.violations` が検査する（スロット、L3、L5、L7、L9。コンパイラの verifier とは独立に書く）。カーネルの DAG とスケジュールから計画を作るつなぎは、`crosscheck` のテストに置く（`FixedPipelines`）
  - 対応する machine は Core と同じで、`CoreParams.unsupported` と同じ理由で拒否する
  - 終了は Core と同じ数え方にする。最後の書込みの境界 E_T の cycle T を HALT の cycle とみなし、E_(T+1) で done を上げる（T+1 cycles）。同じスケジュールは Core と同じ cycles になる
  - 記録する系列は2つと下限である。「VLIW の命令列」は、VLIW の記録の命令列と同じ発行サイクルと同じレジスタ割り当て。「上限なし」は、VLIW と同じ `ListScheduler` を、同じ DAG に、レジスタの上限なしで使う（値は、寿命が重ならないものでレジスタを共有する）。下限は、どの合法な計画にも成り立つ値で、理由を添える
  - FIR の係数は layout の定数の語から LD で読み、回路は係数の値を持たない（係数可変）
- **理由**:
  - 「VLIW の命令列」は、スケジュール・レジスタの数・スロット・Scratchpad が VLIW と同じで、違いは命令メモリ・PC・decoder・RF・違反の検出だけになる。合成（#80）で面積と Fmax を比べれば、プログラマビリティのコストだけを取り出せる
  - 「上限なし」は、VLIW とのスケジュールの違いが RF の容量（16 本）だけになる。cycles の差は RF の容量の効果として読める
  - ループのパイプラインを手で書く方式は、ループの充填と排出、固定の II のためにVLIW より cycles が多くなった（試作で 29 / 68 / 57 cycles）。スケジュールの方式の違いが、プログラマビリティの差に混ざる。Modulo Scheduling から生成する方式は、専用回路らしい小さな制御になるが、コンパイラの変更が要り、同じ記録の表に方式の違いが入る。どちらも #75 では採らず、ループの回路は #80 の候補に残す
  - Core のモジュールをそのまま使うと、資源を揃えたことを、主張ではなく構造で示せる
  - 終了を Core と揃えると、同じスケジュールの cycles が一致し、比較の境界が同じになる。HALT の bundle の1サイクルは、差の表に書く
- **影響**:
  - 既定の構成で、VLIW の命令列は 26 / 65 / 56 cycles（VLIW と同じ）、上限なしは 26 / 63 / 52 cycles、下限は 26 / 62 / 51 cycles（`saxpy8` / `fir4x8` / `matmul3`。[benchmarks/RESULTS.md](../benchmarks/RESULTS.md)）
  - 上限なしの回路は、値のレジスタを VLIW の 16 本より多く使う（`fir4x8` 44 本、`matmul3` 38 本）。これは揃えられない差として記録する
  - 回路の制御は、命令列を焼き込んだものと同じ大きさになり、専用回路を自由に最適化した設計ではない。最適化した回路（ループの制御、係数の焼き込み、演算器の複製）と Fmax・面積の比較は #80 で行う
  - `ComputeSlot` は SUB の演算器も持つ。計画が使わない演算器が合成で消えるかは #80 で確かめる

## ADR-0018: MAC は ISA mvp-1 で入れ、読出しポートは3本のまま規則 L11 で数える

- **状態**: 採用（Issue #69。オーナー判断 2026-10-16。実装は #77）
- **背景**: ADR-0012 で、SIMD より先に MAC を、新しい ISA の版で入れて評価すると決めた。#69 の項目1で、演算の形は3ソース・独立した書込み先 `rd = low32(rs1 × rs2 + rs3)` に決まった（DAG の `a × b + c` をそのまま対応付けられ、結果を c と同じレジスタに置く制約が生じない）。残る契約は、RF の読出しポート（項目2）、ハザードと資源（項目3）、ISA の版と互換性（項目4）である。今の RF は読出し3本（Compute 2 + ST 1）で、MAC は3本を読むので、ST と同じ bundle に置くと4本になる。
- **決定**:
  - ISA の版 `mvp-1` を `mvp-0` + MAC とする（MAC は必須）。1つのコードで両方の版を扱い、machine description で切り替える。`config/machine.json`（mvp-0 revision 2）は変えない。mvp-1 の既定の machine description は `config/machine-mvp1.json`（`vliw2-i32-sp2-mac`）とし、`schema_version` 2 を mvp-1 専用にする
  - MAC は Compute スロットの演算で、3つのソースを発行サイクルに読み、Compute の書戻しポートに書き戻す。既定は latency 2・II 1。MAC は専用の演算器を持ち、L9 は演算ごとに数える（演算器の共有は mvp-1 でも表現しない）
  - 符号化: opcode は machine description から取り（既定 4）、rs3 を Compute word の bits 15:12 に置く。bundle は64bit のまま。ADD/SUB/MUL の bits 15:0 は予約のまま
  - 読出しポートは3本のままにし（M3 での暫定の方式。ADR-0012）、規則 L11 を足す。bundle の読出しの数（オペランドの欄の数。同じレジスタを2つの欄で読んでも2）は `register_file.read_ports` 以下でなければならない。mvp-1 のローダは `read_ports` 3 と 4 を受け付け、既定は3（MAC と ST を同じ bundle に置かない）。RTL は、ポート2のアドレスを MAC の rs3 と ST のソースで切り替えて、3本のまま MAC を入れる
  - 読出し4本の RTL は #57（Phase B）で足す。#77 では `read_ports` 4 の構成を、verifier と参照モデルだけで扱う（制約なしの比較用）。#57 では、MAC の演算器の増分、4本目の読出しポートの増分（3R/2W と 4R/2W の面積）、ポート2のアドレスの選択が Fmax に効くかを、別々に測る
  - #77 Phase A に、MAC の latency だけを3にした構成を、感度の確認として足す（list scheduling と Modulo Scheduling の両方で測る）。latency 2 は、この設計が完成するまでの既定とし、latency 3 の案はこの構成の結果で見直せる
  - mvp-1 の machine description は、#77 Phase A の後に `frozen` にする。#57 で方式を変えるときは revision を上げ、ISA の版は mvp-1 のままにする
  - mvp-0 の記録は `vliw-metrics/1` のままにし、mvp-1 の記録は `vliw-metrics/2` にする（MAC と読出しポートの欄を足す）
- **理由**:
  - mvp-1 = mvp-0 + MAC にすると、「MAC なし」の側が凍結した mvp-0 そのものになり、同じビルドで比べられる。mvp-0 の命令語は mvp-1 でも同じ意味になる
  - 読出し3本の命令列は4本でも合法なので、後から4本に緩めても既存の命令列は壊れない（ADR-0006 と同じく、合法な範囲を保守的に始める）。RF を 3R/2W のまま MAC を入れると、MAC の演算器の増分と4本目のポートの増分を #57 で別々に測れる（ADR-0012 の「1つずつ」）
  - 1つの規則と1つのパラメータで3本と4本の両方を表せ、ADR-0009 の3段の契約（形式・意味論・RTL の範囲）にそのまま乗る。L1 には入れない。verifier は L1 の違反があると、L1 と命令領域の容量（L2）しか報告せず、他の規則の違反が見えなくなるからである
  - latency 2 にすると、`fir4x8` と `matmul3` の Compute の演算が MUL と MAC だけになり、どちらも latency 2 なので、MUL(s) と ADD(s+1) の書戻しポートの衝突（L5）による空きが消える。latency 3 は、パイプラインの段を取りやすい代わりに MAC(s) と MUL(s+1) が衝突する。オーナーは latency 3 とも迷ったので、感度の確認の構成で比べ、その結果で見直せるようにする
  - 見積り（使い捨ての実装で `Dag.build` と `ListScheduler` を移したもの。16本、rematerialization なし。#77 で測る）: 方式ごとに cycles 最小で、`fir4x8` は 65 → 40（read_ports 3・4 とも）、`matmul3` は 56 → 39（read_ports 3）、33（4）、`saxpy8` は 26 → 27（read_ports 3）、26（4）。ループ（演算を数えた値）では、ResMII が `fir4x8`（i）で 7 → 4、`matmul3`（i）で 15 → 9、`matmul3`（m）で 18 → 9 になる。read_ports 3 で3本目の読出しポートを使う数（MAC の数 + ST の数）は、`fir4x8`（i）で 4、`matmul3`（i）で 9 で、ResMII を超えない
- **影響**:
  - ローダと符号化（デコーダ・アセンブラ）には、版ごとの分岐が入る。verifier と参照モデルは、machine description の演算表と `register_file.read_ports` に従うだけで、版では分岐しない。RTL は MAC を持つか（`hasMac`）で、コンパイラは machine に MAC があるかで切り替える。記録は、版によって metrics の形式が分かれる（#77）。規則 L11 は両方の版に共通で、mvp-0 では常に満たされる（L9・L10 を足したときと同じ扱い）
  - read_ports 3 では、MAC を置いた bundle に ST を置けず、スロットの重なりの損失が出る。#77 Phase A で、当たった bundle の数と、read_ports 4 との cycles の差を記録する。M3 での読出しポートの方式は暫定とし、この cycles の差と #57 の面積・Fmax の結果で見直す（ADR-0012）。既定を4に変えるときは、machine description の revision を上げるだけで、ISA と規則は変えない
  - Modulo Scheduling は、読出しポートを資源に足す（read_ports 3 では、3本目の読出しポート（RTL のポート2）を MAC と ST が使う）。予約表があるかの正確な判定（`RowFit`）はスロットの種類ごとなので、どれかの種類で予約表が無ければ、ポートを足しても無い。このときは、今と同じく予約表が無いとする（ADR-0015 の (a)）。read_ports 3 で MAC と ST の両方があり、どの種類にも予約表があるときは、このポートが2つの種類を結び付けるので、2つの種類を一緒に探索して判定する（#77）。read_ports 4 と mvp-0 では、判定は今と同じである
  - 2026-10-16 の補足（#77）: 2つの種類を一緒に探索するのは `RowFit.fitsTogether` である。この場合を「決まらない」とすると先読みが働かず、`fir4x8(i)` と `matmul3(i)` で、それぞれ II が1つ上がった（read_ports 3 で 5 と 10。一緒に探索すると 4 と 9）
  - 2026-10-16 の補足（#77）: RTL の MAC は、出力する Verilog で乗算器を MUL と共有する（firtool が2つの積をまとめる）。#57 で MAC の演算器の面積を測るときは、これを考慮する

## ADR-0019: 読む側が1つの MUL とそれを読む ADD を MAC に融合し、ループでは MII が上がるときは融合しない

- **状態**: 採用（Issue #69 の項目5。オーナー判断 2026-10-16。実装は #77）
- **背景**: MAC（ADR-0018）を使うには、コンパイラが DAG の `MUL + ADD` を MAC に置き換える必要がある。MUL の結果が他でも使われるとき、依存の鎖が延びるとき、ループの累算の閉路が延びるときの扱いを決める必要があった。比較（#77 Phase A）は、同じカーネル・入力・配置・スケジュール戦略で、MAC のある構成とない構成を比べる。
- **決定**:
  - list scheduling: machine に MAC があるとき、読む側が1つだけの MUL と、それを読む ADD を、常に1つの MAC にする。`ADD(m, m)` は融合しない。`ADD(MUL, MUL)` は後の MUL を融合し、先の MUL を残す。SUB の形と、読む側が複数ある MUL は融合しない
  - 融合は戦略の次元にしない（ADR-0016 の rematerialization と同じ扱い）。DAG は、カーネルと machine だけで決まる
  - ループ（Modulo Scheduling）: 同じ規則で融合し、融合した後の MII が大きくなるループでは融合しない。MII は読出しポートの資源を除いて比べる（read_ports 3 と 4 で、融合したグラフが同じになり、cycles の差が制約だけの効果になる）
  - read_ports 3 の list scheduling は、#77 Phase A では素朴な方法に固定する。Compute を先に埋め、MAC を置いた bundle では ST を待たせる。読出しポートの検査は `ListScheduler` の `free()`（レジスタの上限以外の制約）に入れる（rematerialization の「詰まり」の判定を誤らないため）
- **理由**:
  - 読む側が1つの MUL だけを融合すると、乗算の数は増えず、値を計算し直さない（ADR-0016 は計算した値を複製しない）。3つのカーネルの組を全て取れる（`fir4x8` 24、`matmul3` 18、`saxpy8` 8）
  - 試行ごとに融合しない DAG と比べる方式は、どの行も悪くならない代わりに、制約の損失を隠し、DAG が行ごとに変わる。下限で全体を判定する方式は誤判定する
  - ループで常に融合すると、累算の閉路が ADD の1から L_MAC に延び、RecMII が上がることがある。MII で判定すると、それを止められる
  - read_ports 3 の損失を測るには、まずスケジューラの工夫を入れずに測る。工夫で減らせるかは、その後の結果である
- **影響**:
  - DAG のノードは3オペランドになり、`Dag.split`（rematerialization）、コード生成、ループ IR、`ModuloTrace` が3ソースを扱う（#77）
  - 融合した DAG では依存の鎖が延びるので、依存が律速のカーネルでは MAC で遅くなることがある（直線の `dot16` の試算で、MAC なしの 42 cycles に対し、latency 2 では 37 cycles に縮むが、latency 3 では 52 cycles に延びる）

## ADR-0020: Verilator と JDK の版を1か所で決め、版を変える前に候補を対照と同じ run で試す

- **状態**: 採用（Issue #121。オーナー判断: 2026-10-17 に #121 の §2（目標の版、Issue にすること、`--verilate-jobs 1` を外す条件）、2026-10-18 に §8 の 4（JDK の版も同じ properties で決める））
- **背景**: Verilator の版は、3つの workflow の `apt-get install -y verilator` と、テストの定数（`BenchmarkRecords.PinnedVerilator`）で決まっていた。apt の行は版を指定しない。5.020 になるのは、ubuntu-24.04 の apt に 5.020-1 しかないからである。JDK の版も、3つの workflow に同じ値が書いてあった。版がずれると、`sbt test` は約5分後に `BenchmarkSpec` で初めて失敗した。Verilator を上げれば ADR-0013 の回避策を外せる見込みがある。しかし、今の main のテストは、5.020 以外の版でまだ走らせていない。また、エージェントの session からの workflow_dispatch は 403 になる（[PHASE3.md](PHASE3.md)）。
- **決定**:
  - 版は [project/toolchain.properties](../project/toolchain.properties) の1か所に書く。キーは `verilator.version`、`verilator.apt` と `verilator.commit`（apt のパッケージの版か、ソースの commit。ちょうど一方を書く）、`jdk.major` である
  - 書式は厳しくする。行は、空行、`#` で始まるコメント、`key=value` のどれかとする。キーは決めたものだけで、重複、CR、タブ、行末の空白、NUL は誤りとする。読み手はテストの `vliw.hw.Toolchain` と `scripts/toolchain.sh` の2つで、同じファイルから同じ値を読む（`ToolchainSpec` が確かめる）
  - テストは、PATH の Verilator が期待する版であることと、JDK が `jdk.major` であることを確かめる（`BenchmarkSpec`）。`scripts/check.sh` と `scripts/mutation-check.sh` は、sbt の前に `scripts/toolchain.sh check` で Verilator の版を確かめる
  - 期待する版は、固定の版とする。`VLIW_VERILATOR_EXPECTED` で上書きできるのは、手元（`GITHUB_ACTIONS` が空）と、候補を試す workflow（`.github/workflows/toolchain-candidates.yml`）だけとする。それ以外で設定するか、空文字列にすると失敗させる。テストの JVM は `[toolchain] verilator=<PATH の版> expected=<期待する版> (pinned|env)` の行を出し、CI の `scala` ジョブは、すべての行が `(pinned)` であることを確かめる
  - Verilator と JDK を入れる処理は、CI の action の1か所にする（#121 の PR 2）。それまでは、3つの workflow の apt の行と `java-version` が残る。それらが properties と同じ版を入れたことは、テストと `scripts/toolchain.sh check` が確かめる
  - 候補の版は、固定の版を対照にして、同じ run で PR から試す（#121 の PR 3）
  - 版の変更と、回避策（ADR-0013 の `--verilate-jobs 1`）の変更は、別の PR にする
  - R1: 記録（`benchmarks/`）は JVM のコードが計算する。シミュレータは確かめるだけにする
  - R2: 版を変えて変わってよいのは、`benchmarks/RESULTS.md` のツールの行と、`metrics` の `generator` 欄だけとする。`benchmarks/`・`tests/cases`・`tests/golden` に他の差分が出たら、その版にはしない。候補を緑にするために、記録を作り直さない。ツールの行は、候補を試す実行でも固定の版を書く
  - R3: 乱数の seed は、Verilator の版と一緒に記録する（`seed.txt` と `[sim-seed]` の行。`VLIW_SIM_SEED=1 (default) verilator=5.020` の形）
- **理由**:
  - 版の切り替えと戻しが、properties の1行と、生成し直すツールの行で済む。戻すのは revert 1つである
  - 書式を厳しくすると、Scala と shell の2つの読み手が、同じファイルから違う値を読むことがない
  - 版のずれが、sbt の前に、直し方と一緒に分かる。mutation では、ずれた版のために全 mutant が KILLED に見えることもない
  - 上書きを手元と候補の workflow に限ると、必須の CI は固定の版でしか緑にならない
  - 候補と対照を同じ run で走らせると、runner や main の違いと、版の違いを分けられる。PR から起動するのは、エージェントの session からは workflow_dispatch ができないからである
  - 版と回避策を別の PR にすると、失敗したときに、どちらが原因かを分けられる
  - R1 があるので、版を変えても記録の数値は変わらないはずである。R2 は、それが崩れた版を採らないための決まりである。同じ seed でも、版が違えば乱数の値が違うことがある（5.046 から）。そのため R3 で版を残す
- **影響**:
  - ADR-0004 の表の、JDK と Verilator の固定場所を置き換える。この2つは、版を変えても ADR-0004 の表を変えない。版の採り方（リリースから2週間以上経った版）と、他のツールの固定は ADR-0004 のままである。Chisel・firtool・Scala・sbt の版は、今までどおり `build.sbt` と `project/` で決める
  - ADR-0013 の理由「Verilator の版は ADR-0004 で固定しており、CI の環境では上げられない」を置き換える。版は properties の1行で変えられ、候補は PR から試せる。上げるかどうかは、候補の結果で決める。ADR-0013 の決定（1スレッドの verilation と、seed の明示）はそのままである。回避策を外すときは、別の ADR にする（#121）
  - 調べた経過と数値の記録先を、ADR-0013 の #74 から、#121 と [docs/toolchain/](toolchain/README.md) に移す。版を変える手順、手元で入れる方法、版の履歴も [docs/toolchain/README.md](toolchain/README.md) に置く。ADR は書き換えないので、手順と履歴は ADR に書かない
