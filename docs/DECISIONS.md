## ADR-0001: 実装言語をScalaに統一する

- **状態**: 採用（Issue #2）
- **背景**: Phase 0のアセンブラ・encoder・verifier・参照モデルの実装言語を、PythonとScalaから選ぶ必要があった。
- **決定**: Phase 0〜2のソフトウェアも、Phase 1のChisel RTLもScalaで実装する。
- **理由**:
  - machine description、命令表現、トレース形式を、ビルド上の依存関係としてRTL生成器と直接共有できる。
  - ビルド・テスト・CIが1系統（JDK + sbt）で済む。
  - 「別言語なら参照モデルが独立する」という利点は小さい（ADR-0002）。
- **影響**: `compiler/`・`sim/`・`hw/` はすべてsbtのサブプロジェクトになる。Python実装は作らない。

## ADR-0002: 相互検査は言語ではなく状態表現と判定方法の違いで設計する

- **状態**: 採用（Issue #2。具体化は #8, #9, #10）
- **背景**: 参照モデル・verifier・RTLが同じ誤りを共有すると、相互比較しても誤りを検出できない。実装言語を変えても、同じ人が同じ解釈で書けば誤りは共有される。
- **決定**: 独立性は次の3点で確保する。
  1. **状態表現を変える**: 参照モデルはサイクルごとのpending操作キューで値を計算する。verifierは値を持たず、資源予約表とレジスタの書込み中区間で判定する。
  2. **判定方法を変える**: 参照モデルは実行して、実行時の違反（同一境界の二重書込みなど）を検出する。verifierは命令列だけから静的に合法性を判定する。
  3. **期待値を手で作る**: ISA.mdの命令例のように、commit時刻・最終状態・cycles・拒否理由を人が書いたテストケースを基準にする。モデルの出力をそのままgoldenとして採用する前に、手作りの期待値と照合する。
- **ビルド上の強制**: `compiler`（verifierを含む）と `sim` は `isa` にのみ依存し、互いに依存しない（`build.sbt`）。両者を突き合わせるテストは、テスト専用のプロジェクト `crosscheck` に置く。
- **影響**: 実行意味論は #5 で文書として先に確定し、各実装はその文書から独立に導く。

## ADR-0003: Lean 4は仕様確定後に小さな対象へ限定して導入を検討する

- **状態**: 採用（導入の判断は保留）
- **背景**: 形式検証は決定論性の主張と相性が良い。一方で、仕様が動いている段階で組み込むと重い。また、証明を書かない場合のLean 4は普通の関数型言語であり、書き手が少ないため開発支援（AIエージェントを含む）の精度も下がる。
- **決定**: Phase 0〜1では導入しない。ISAと実行意味論が安定した後、小さな検証対象に限定して導入を検討する。
- **候補**: encoder/decoderの全単射性。MVPの合法性規則の下で、実行サイクル数が入力値に依存しないこと。verifierの規則が意味論上の違反をすべて含むこと。

## ADR-0005: CIの入口と起動条件

- **状態**: 採用（Issue #3）
- **決定**:
  - 手元とCIの入口を `scripts/check.sh` に一本化する。CIのジョブはこのスクリプトを呼ぶだけにする。
    - `static`: JSON構文、shellcheck、追跡ファイルの空白エラー
    - `scala`: `sbt scalafmtSbtCheck scalafmtCheckAll test`
  - 起動条件は、`main` へのpush、すべてのPR、手動実行とする。作業ブランチではPRを開いてCIを回す。（当初は全ブランチへのpushで起動し、PRでは二重実行を避けてジョブを`if`で飛ばしていたが、PR上に同名のskippedチェックが並び紛らわしいため変更した。）
  - `permissions: contents: read` にする。`main` 以外では、同じrefの古い実行をキャンセルする。
  - 使用するActionは、公式（`actions/*`）とsbt公式（`sbt/setup-sbt`）のメジャータグで固定する。第三者のActionを追加する場合はcommit SHAで固定する。
- mutation チェック（`scripts/mutation-check.sh`）は遅いため、別のワークフロー `mutation.yml` で、手動実行とmutantの定義を変えたPRでだけ実行する（#33）。
- `scala` ジョブ（と `mutation` ジョブ）は Verilator を apt で入れ、`hw` の ChiselSim テストも実行する（#23）。firtool は sbt の依存として取得し、sbt のキャッシュに載る。
- 間欠的な失敗を追えるよう、`scripts/check.sh` は sbt の出力・環境・プロセスの記録・テストの並行性の実効設定を `build/check-logs/` に残し、`scala` ジョブは失敗したときにそれらと ChiselSim の作業ディレクトリ・JUnit レポートを artifact として残す。テストのステップには job より短い timeout を付け、止まったときも artifact を残せるようにする。`mutation` ジョブは mutant ごとの判定とログを常に残す。繰り返し実行のワークフロー `repeat-tests.yml` は手動実行だけとする（#74）。

## ADR-0006: MVPでは合法なプログラムを保守的に限定する

- **状態**: 採用（Issue #5）
- **背景**: ハザード検査の実装方法を決める前に、命令がいつ値を読み、いつ状態を更新するかという実行意味論を確定する必要があった。現行ISAの骨格（発行サイクルで読む、固定レイテンシー後にcommitする、同一bundle内の直接転送なし）は既に明確だった。
- **決定**: 骨格はそのまま保ち、[ISA.mdの「実行意味論」](ISA.md#実行意味論)として文書化する。合法なプログラムは[「MVPの合法性規則」](ISA.md#mvpの合法性規則) L1〜L8 に限定する。意味論上は値が定義できても、次の使い方は不正とする。
  - 書込み中のレジスタを読み、旧値を利用すること（L3）
  - 同じレジスタへの書込みを重ねること（L4）
  - 入力宣言されていない値を読むこと（L8）
  - HALTを最後以外のbundleに置くこと（L2）
- **理由**:
  - 合法なプログラムでは、各レジスタの値が「最後にcommitされた書込み」だけで決まる。実行中の操作の順序や、ハードウェアのパイプライン内部状態に依存しない。そのため、verifier・参照モデル・RTLが独立に実装しても一致を確認しやすい。
  - MVPのカーネル（展開済みの固定長ループ）では、これらの使い方は不要である。
  - 規則は後から緩められるが、一度許したものを禁止するとプログラムの互換性が失われる。
- **影響**:
  - verifier（#9）は、書込み区間・書戻しポートの予約・入力宣言を使って、L1〜L8を静的に判定する。
  - 参照モデル（#8）は、同じ違反を実行中に検出する。
  - テストケース（#7）は、入力宣言 R_in / M_in を持つ。
  - `config/machine.json` に `instruction_memory.bundles`（256）と `timing.source_read` を追加した。

## ADR-0007: machine.jsonは手書きの厳格なローダで検証し、JCS互換の正規化形式で識別する

- **状態**: 採用（Issue #4）
- **背景**: RTL・命令列・シミュレータが同じ定義を参照するためには、定義の検証方法と同一性の判定方法が必要だった。
- **決定**:
  - 検証は、JSON Schemaではなく、Scalaの手書きローダ（`vliw.isa.MachineDescription`）で行う。規則は [MACHINE.md](MACHINE.md) にまとめる。
  - JSONの読み書きには ujson を使い、重複キーを拒否する厳格な読み込みを被せる。
  - 同一性は、正規化形式（RFC 8785を整数に制限したもの）のSHA-256で表す。`schema_version`（形式の版）と `revision`（内容の版）は分けて持つ。
- **理由**:
  - mvp-0 には、値が1つに固定された項目が多い。「この実装が対応する値か」を判定するには、型の検査だけでなく値の検査が必要で、ローダと同じ場所に書く方が一貫する。
  - JSON Schemaの検証器を追加すると依存が増える。またScalaのモデルとschemaの二重管理になる。
  - 正規化形式は、ASCIIと整数だけの文書では `jq -cS .` と一致する。そのため、外部ツールでも同じhashを再計算できる。
- **影響**: ローダの規則を変えるときは `schema_version` を上げる。CIの `static` ジョブは引き続きJSON構文だけを確認し、意味の検証は `scala` ジョブのテスト（`MachineDescriptionSpec`）が行う。

## ADR-0008: アセンブリ構文とテストケース形式は isa に置く

- **状態**: 採用（Issue #7）
- **背景**: テストケースは、verifier（`compiler`）と参照モデル（`sim`）の両方が読む。`sim` は `compiler` に依存できない（ADR-0002）ため、どちらかに置くと片方から読めない。
- **決定**: アセンブラ、逆アセンブラ、テストケースのローダ、規則IDの一覧（`Rule`）を `isa` に置く。これらは命令の**表記**と**入力・期待値の形式**だけを扱い、実行意味論や合法性の判定を含まない。
- **形式**: テストケースはJSONとし、命令列は文字列の配列として埋め込む（[TESTCASE.md](TESTCASE.md)）。machine description と同じ厳格なローダを使える。命令列も1行1要素で読める。
- **影響**: `compiler` は Phase 2 のスケジューラと verifier を担う。アセンブラは `compiler` に置かない。

## ADR-0009: machine description の契約を3段に分け、II と書込み中のメモリ語を合法性規則にする

- **状態**: 採用（Issue #35。第三者レビュー P1）
- **背景**: ローダは `ii` と `latency` を1〜8で受け付けるが、verifier と参照モデルは II を検査せず、RTL は一部の構成だけを実装していた。どの構成をどこまで扱えるかが文書になく、構成を変えた実験で契約が割れるおそれがあった。また ST のレイテンシーが2以上のとき、書込み中の番地を LD で読む（旧値を読む）ことの扱いが未定だった。
- **決定**:
  - 契約を、形式（ローダ）・意味論（verifier と参照モデル）・RTL（`CoreParams`）の3段に分ける。ローダが受け付ける構成は、すべて意味論で扱う。RTL の対応範囲は別に定め、範囲外は組み立て時に拒否する（[MACHINE.md](MACHINE.md)「実装ごとの対応範囲」）。
  - II は、演算ごとの専用の演算器の発行間隔とする。同じ演算の発行は II 以上空ける（L9）。演算器の共有は mvp-0 では表現しない。
  - 書込み中のメモリ語の読出しを禁止する（L10）。レジスタの L3 と同じ扱いで、旧値が定義されていても不正とする。
- **理由**:
  - II を検査しなければ、II が2以上の構成で、verifier・参照モデルが II を守らない命令列を合法と判定してしまう。拒否するより規則にする方が、Phase 2 のスケジューラで資源予約を試せる。検査の実装も小さい。
  - L10 は、ADR-0006 の方針（実行中の操作の時刻に依存するプログラムを排除する）に従う。旧値の読出しを許すと、ST のレイテンシーを伸ばす RTL は旧値を保持する仕組みを持つ必要がある。規則は後から緩められる。
  - 汎用ローダで RTL の非対応値を一律に拒否すると、ソフトウェアだけで行う実験（`slow_units.json` など）ができなくなる。
- **影響**:
  - 凍結した `config/machine.json`（revision 2）は、全 II が1、ST のレイテンシーが1なので、L9・L10 は常に満たされる。既存の判定・hash・ISA バージョン（`mvp-0`）は変わらない。
  - 構成を変えたテストケースは判定が変わることがある（`slow_store_then_load` は L8 に加えて L10 に違反する）。
  - verifier と参照モデルの差分テストに、II が2以上の構成（`tests/machines/ii_units.json`）を加えた。

## ADR-0010: カーネルDSLは Scala 内部DSLとし、配置と lowering を分ける

- **状態**: 採用（Issue #47）
- **背景**: Phase 2 では、SAXPY・FIR・行列積を自動で命令列にし、構成を変えて比べる。そのための入力の書き方と、意味（期待値）を決める必要があった。
- **決定**:
  - Scala の内部DSLとする（[DSL.md](DSL.md)）。ループは Scala の `for` で展開する。値は32bitの整数で、2^32 を法とする。
  - 式は、物理レジスタ・発行サイクル・アドレスを持たない仮想値（`Expr`）として表す。DAG、スケジューリング、レジスタ割り当ては後の段階で行う。
  - Scratchpad のアドレスは DSL に書かず、別の処理（`MemoryLayout`）で決める。初期実装は固定順の割り当てとする。
  - スカラーと定数は、初期化済みメモリの読出しに lowering する（現在の ISA に即値演算が無いため）。
  - 意味は、DSL を直接評価する参照実装（`Interpreter`）で定める。テストでは、DSL を使わない素の Scala の実装とも比べる。
  - 入力は読出し専用、出力は書込み専用で、各出力要素にちょうど1回だけ代入する。
- **理由**:
  - 目的は将来のアーキテクチャ比較で、DSL の機能ではない。内部DSLならパーサが要らず、Scala の型検査と `for` をそのまま使える（[ADR-0001](#adr-0001-実装言語をscalaに統一する)）。
  - 配置と DSL を分けると、配置の方法（bank を考えた割り当てなど）を変えて比べられる。
  - 読出し専用の入力と書込み専用の出力なら、3つのカーネルを書けて、メモリ操作の alias が起きない。DAG（#48）の最初の実装が単純になる。
- **影響**: SAXPY は `y = a*x + y` を上書きせず、別の出力配列に書く。上書きや中間配列が必要になったら、制約を緩め、DAG にメモリ順序の依存を加える。

## ADR-0011: Phase 3 のループは ISA を変えずに展開し、IR に反復の情報を残す

- **状態**: 採用（Issue #67、オーナー判断 2026-10-15。第三者レビューの推奨）
- **背景**: Modulo Scheduling は反復を重ねる手法で、反復の単位と反復をまたぐ依存（RecMII）が要る。mvp-0 には分岐もループも無く、Phase 2 の DSL は組み立て時に完全に展開するので、DAG には反復の情報が残らない。
- **決定**:
  - mvp-0 の ISA は変えない。Modulo Scheduling の結果は、有限の反復回数からプロローグ・定常・エピローグを直線の bundle 列に展開して出力する（案A）
  - DSL または IR に、反復の境界、反復距離付きの依存、最小限のループ内の状態を残す（#76）
  - 演算器の II（`operations.<op>.ii`、L9）と、ループの II（反復の開始間隔。`vliw-metrics/1` の `ii` 欄）を別の概念として扱う
  - 展開した結果が命令領域（`instruction_memory.bundles`）を超える場合は、展開できないと報告する
  - ISA の固定回数ループ命令（案B）は先送りする（#81）
- **理由**: ISA・verifier・参照モデル・RTL を変えずに、Modulo Scheduling そのものの効果と限界を先に測れる。ループ命令を同時に入れると、命令領域の大きさやループ制御のオーバーヘッドの影響と切り分けられない。
- **影響**: ADR-0010 の「ループは Scala の `for` で展開する」を部分的に置き換える（ループ構造を IR に渡す経路を #76 で足す。完全に展開する既存の書き方は残してよい）。最終の命令列は既存の verifier（L1〜L10）・参照モデル・RTL でそのまま検査できる。反復回数は命令領域の容量で制限される。案Bは、M3 の結果（命令領域に収まらないカーネル、命令数と cycles）と、案Bのループ制御の cycles の見積りを材料に判断する（#81）。

## ADR-0012: MAC を先に導入して評価し、SIMD は後に分ける

- **状態**: 採用（Issue #69、オーナー判断 2026-10-15。第三者レビューの推奨）
- **背景**: Phase 2 の `fir4x8` と `matmul3` は Compute スロットが律速で、MUL と ADD の組が多い。MAC・SIMD・Compute スロットの増設を同時に入れると、どの変更が cycles・面積・Fmax に効いたかを切り分けられない。
- **決定**:
  - Milestone 3 では MAC だけを扱う。契約（演算の形、RF の読出しポート、ハザード、Latency・II、エンコード、ISA の版）は #69 で決め、実装と、MAC のある構成とない構成の cycle ベースの比較は #77 で行う
  - Fmax・面積・RF の増分のコスト（Phase B）は、#77 の構成を使って合成評価 #57 で行う。M3 で選ぶ読出しポートの方式は暫定とし、その結果で見直す
  - SIMD と Compute スロットの増設は、MAC 単独の効果を測った後に、別の実験として設計する（#78）
  - 凍結した mvp-0（revision 2）は変えない。MAC は新しい ISA の版で入れる
- **理由**: 変更を1つずつ入れると、効果の原因を切り分けられる。MAC は cycles を減らしても、RF のポートや演算器の面積を増やし得るので、cycle と面積・Fmax を分けて評価する必要がある。
- **影響**: ROADMAP の Phase 3 は「Modulo Scheduling、MAC」とし、SIMD は MAC の評価の後に置く。
