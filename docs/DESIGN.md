# 設計方針：最小VLIWから固定サイクルのストリーミング処理系へ

作成日：2026-10-14（日本時間） / 状態：初期設計案

## 目的

高スループットと予測可能なレイテンシーを両立するため、最小限のVLIW的コンパイラと実行系を共同設計する。Chiselを使って演算器とメモリ構成を段階的に変更し、コンパイラ・参照モデル・RTL間でサイクル単位の一致を確認する。

中心原則は「コンパイラが時間配置を決め、ハードウェアがそのスケジュールを実行する」。最初の成功条件はピーク性能ではなく、正しい演算結果と固定実行サイクル数の同時成立である。

## 技術的な位置づけ

以下は設計上の対応関係であり、特定製品との実装互換性を主張しない。

| 系譜 | 取り込む考え方 | 本計画への適用 |
|---|---|---|
| VLIW / DSP | 命令並列性と静的な資源割当 | 演算とLoad/Storeを別スロットに配置 |
| Patmos / T-CREST | 時間予測可能性を設計要件とする | メモリ・競合・完了時刻を仕様化 |
| Synchronous Dataflow | 既知の生成・消費率に基づく静的計画 | 固定サイズのストリーム、後続のバッファ容量設計 |
| PRET | 時間を実行基盤の契約として扱う | 保証範囲とI/O境界の定義 |
| TTA / OpenASIP | 転送・資源構成とコンパイラの共同設計 | データ移動を明示化する拡張の比較対象 |
| Calyx / CIRCT Scheduling | 制御・時間契約・資源制約の表現 | 独自IRとスケジューラの設計参考 |
| Groq型ストリーミング | 演算と通信の事前計画 | 複数レーン・複数タイルへの長期的方向 |
| CGRA / Spatial Dataflow | グラフの配置と通信経路の制御 | 多タイル化後の選択肢 |

これらの比較はプロジェクトの設計判断である。2026年の個別製品仕様や最新バージョンは、この計画の成立条件に含めない。一次資料は[REFERENCES.md](REFERENCES.md)で管理する。

## 決定論性の保証範囲

MVPで保証する対象は、**入力・命令・出力領域の準備が完了し、startを受理してからdoneを通知するまでのクロックサイクル数**。

前提条件は次のとおり。

- 固定クロックで動作し、実行中にreset・割込み・クロック停止が起きない。
- 命令と入力は開始前にローカルに配置され、ホストは実行中に内部状態を変更しない。
- 演算器は固定Latency/II契約を満たし、命令列は独立した検証器に合格している。
- 内部にデータ到着待ち、可変時間のメモリアクセス、動的資源調停を入れない。

ホスト待ち時間、DMA、外部DRAM、ネットワーク、OSは初期保証の対象に含めない。実時間の保証には別途タイミングクロージャとクロック条件の検証が必要である。VLIW方式だけで決定論性は成立しない。

## 最小構成

| 要素 | 初期案 | 理由・制約 |
|---|---|---|
| Issue | Compute 1＋Memory 1 / cycle | 演算と転送の重畳を検証 |
| データ型 | 32bitビットベクトル | ADD/SUB/MULは下位32bit、mod 2^32 |
| RF | 16レジスタ、3 read / 2 write | Compute 2読出し＋ST 1読出し。書込はCompute/Memory各1 |
| 演算 | ADD/SUB L=1、MUL L=2、各II=1 | 時間配置とパイプラインの検証 |
| Scratchpad | 2 bank × 256 word、各bank 1RW | 1スロットなので初期は全体で1アクセス/cycle |
| LD | issueからRF可視化までL=2、II=1 | SyncReadMem読出しとRF格納を分ける |
| ST | メモリ更新までL=1、II=1 | 計算と独立して完了を予約 |
| 命令 | 64bit bundle、専用ローカル命令領域 | 小規模の組合せ読出しROMから開始 |
| 制御 | start / busy / done、PC、HALT | 固定回数ループは当初展開し、専用ループ制御は後続 |

3R/2W RFは小容量レジスタによる初期モデルであり、一般的なSRAMマクロでそのまま実現できる前提ではない。面積と配線遅延を合成で評価する。2バンク化だけではアクセス帯域は2倍にならず、将来のスロット・ポート拡張が必要である。

## ハードウェア・コンパイラ間の契約

`config/machine.json`を共有定義の起点とする。将来的に同一定義からChiselのパラメータ、エンコーダ、検証器、参照モデルの設定を生成する。

機能ユニットのLatencyとIIを別に定義する。依存辺u→vでは、開始サイクルをs、LatencyをLとして `s_v >= s_u + L_u` を満たす。

発行スロットだけでなく、以下を検証する。

1. 各演算器のIIと占有資源。
2. 書き戻しポートを使う未来サイクル。MULと次サイクルのADDが同時完了する場合も検出する。
3. RFのRAW/WAR/WAW、同一サイクルの二重書込、ソース値の生存期間。
4. Scratchpadのアドレス範囲、bank、read/write競合、必要なメモリ順序。
5. HALT時点の全操作の完了と、doneの正確な時刻。

検証器はスケジューラから独立させ、手書き・生成済みのどちらの命令列も検査する。ハードウェアのassertionは違反検出に使い、通常実行時にハザードを隠す自動ストールは導入しない。

## Chiselの開発フロー

- `chipsalliance/chisel-template`を参考に`hw/`のビルドを整備する。初期資料のリポジトリをテンプレートで丸ごと上書きしない。
- 実装開始時に動作確認したテンプレートcommit、Scala、Chisel、compiler plugin、JDK、ビルドツール、Verilatorを固定する。
- Chisel → FIRRTL/CIRCT `firtool` → SystemVerilogの経路を使う。`firtool`は採用Chiselに互換性のあるものを使う。
- ChiselSimをRTL検証の第一候補とし、採用バージョンのAPIを公式資料で確認する。
- `Module`、`Bundle`、レジスタ、`SyncReadMem`、assertionを基本とする。メモリ競合時の未定義動作に依存しない。
- 外部ready/validは境界で使い、開始前の入力充足と出力容量を保証する。内部スケジュールの停止条件として使わない。

ChiselのRTL生成経路と、カーネルをVLIW命令へ変換するコンパイラは別物である。CIRCT Schedulingも独自ISA向けの完成済みバックエンドではない。

## コンパイラの開発フロー

最初は小さなアセンブラと参照モデルを作り、次に Kernel DSL → DAG → resource-constrained list scheduling → register allocation → schedule verification → bundle encoding を実装する。レジスタ割当が競合を増やす場合は再スケジュールし、最終命令列を再検証する。

固定サイズのループは展開して開始し、Modulo Schedulingはその後に導入する。最初からLLVMバックエンド全体を実装する必要はない。LLVM/MLIR・CIRCT連携はIRと時間契約が安定した段階で判断する。

## 評価と拡張

整数SAXPY、FIR、固定サイズ行列積を使い、結果一致、実行サイクル、定常II、資源使用率、バンドルのNOP率、メモリ帯域を記録する。合成後には面積・最高動作周波数を追加し、電力は測定条件を明記できる段階で扱う。

同じ算術仕様の単一発行モデルと固定パイプラインを比較対象とする。固定パイプラインとの差から、命令メモリ・制御・RFによるプログラマビリティの費用を評価する。比べる系列は、(a) 単一発行、(b) 2スロットの VLIW、(c) 資源条件を揃えた固定パイプライン（#75、ADR-0017。VLIW の命令列を焼き込んだものと、レジスタの上限なしでスケジュールしたもの）、(d) 自由に最適化した固定パイプライン（#80）である。

拡張は、同じカーネル・入力・配置・スケジュール戦略で、拡張のある構成とない構成を比べる。MAC は、mvp-0 と、MAC のある ISA mvp-1 の構成（読出しポート3本の既定、制約のない4本、MAC の latency 3）を比べた（#77、ADR-0018。[benchmarks/MAC.md](../benchmarks/MAC.md)）。cycle だけの比較で、面積と Fmax は #57 で測る。

拡張順は、パイプライン最適化 → Modulo Scheduling → MAC → SIMD → DMA/Double Buffer → 複数タイル/静的通信（MAC と SIMD を分ける理由は ADR-0012）。動的なホスト側制御と、固定時間のカーネル実行を分離する方針を保つ。
